# Sailplay application SDK v1

The SDK provides application, presentation-session and navigation contracts,
Python provider/client helpers, and a Qt5 client that can be registered in QML.
Applications expose the interfaces on their own session-bus service identity.

## Installed files

| Path | Contents |
|---|---|
| `/opt/sailplay/sailplay_sdk` | Python helpers and canonical XML |
| `/usr/share/dbus-1/interfaces/org.sailplay.App1.xml` | Application contract |
| `/usr/share/dbus-1/interfaces/org.sailplay.Session1.xml` | Presentation-session contract |
| `/usr/share/dbus-1/interfaces/org.sailplay.Navigation1.xml` | Provider-neutral navigation contract |
| `/usr/share/sailplay-sdk/qt` | Qt source and qmake include |
| `/usr/share/sailplay-sdk/examples` | Python/Qt clients, reference backend and activation metadata |

The RPM installs these files together with Sailplay. A Python wheel built from
this repository also includes `sailplay_sdk` and its XML. Wheel builds use a
current pip and Setuptools 77 or later on the build host.

## Wire contract

The default application path is `/org/sailplay/v1/App`. An application may
declare another versioned path in its desktop metadata. Interface versions
remain explicit in their names.

`org.sailplay.App1` exposes read-only `ApiVersion`, `ApplicationId`, `InstanceId`
and `Capabilities` properties. `OpenSession(presentation, requiredCapabilities)`
returns a caller-owned session object. Presentations are `phone` and `car`.
Required capabilities are matched against the application's advertised list.
The base capabilities are `state` and `actions`.

`org.sailplay.Session1` provides the following operations.

| Member | Behavior |
|---|---|
| `GetSnapshot` | Return the current `uint64` revision and `a{sv}` state |
| `SetActive` | Update whether the presentation is active |
| `Invoke` | Accept a request ID, action, `a{sv}` parameters and expected revision |
| `Close` | Release this presentation session |
| `StateChanged` | Deliver a complete replacement snapshot and its revision |
| `RequestFinished` | Deliver request ID, revision, result and error fields |

State and parameters use native D-Bus variants. Applications define the keys,
value types and action semantics within their advertised capabilities. String
keys are nonempty. Qt proxies are generated by qmake from the canonical XML.
The Python helpers read the same XML for method and signal signatures.
The Python provider checks each incoming SDK method's wire signature.

Request IDs start at one and increase within a session. Reusing an accepted ID raises
`org.sailplay.Error1.DuplicateRequest` before executing work. The method reply
acknowledges acceptance. Completion arrives asynchronously through
`RequestFinished`, including for an action that completes immediately.

Expected revision zero permits an unconditional operation. A nonzero revision
is checked before dispatch and before committing a replacement state supplied
to `Invocation.complete`. A stale admission fails the method. A conflict during
completion finishes the request with `org.sailplay.Error1.StaleRevision`.
Revisions increase when state changes.

The provider has a fresh `InstanceId` for every backend instance. Clients clear
their cached state when the service owner changes and obtain a new snapshot
after reconnecting. Clients subscribe before requesting the first snapshot and
keep the highest revision received within that instance.

The SDK sources use GPL-3.0-or-later. The RPM installs the notice in
`/usr/share/sailplay-sdk/LICENSE`. Application integrations carry that notice
with their embedded provider. [License](../LICENSE)

## Session ownership and lifecycle

Each presentation belongs to the unique D-Bus name that opened it. Other
callers receive `org.sailplay.Error1.NotOwner` when accessing that session.
State and request-completion signals are addressed to the owning caller.
The provider releases sessions when their caller disconnects from the bus.

Qt and Python session clients acquire a unique temporary
`org.sailplay.Client.c<uuid>` name before activating the backend. They keep the
name through backend-owner changes and release it on close. On a supplied bus,
each client releases only its own name. Sessions and signals continue to use
the caller's unique bus owner.

Sailjail providers need scoped outgoing permissions for the directed SDK
signals. Add these rules to the application's additional permission profile.

```text
dbus-user.call org.sailplay.Client.*=org.sailplay.Session1.StateChanged@/org/sailplay/v1/*
dbus-user.call org.sailplay.Client.*=org.sailplay.Session1.RequestFinished@/org/sailplay/v1/*
dbus-user.call org.sailplay.Client.*=org.sailplay.Navigation1.GuidanceChanged@/org/sailplay/v1/*
dbus-user.call org.sailplay.Client.*=org.freedesktop.DBus.Properties.PropertiesChanged@/org/sailplay/v1/*
```

The installed Sailfish D-Bus proxy uses the caller's well-known name to apply
these permissions to its unique owner. A sandboxed SDK client also needs
`dbus-user.own org.sailplay.Client.*` in its permission profile. Clients making
raw D-Bus calls should acquire a name in that namespace before backend
activation and retain it until their sessions close.

Closing a view should call `Close`. `SetActive(false)` keeps the session while
its presentation is hidden. Applications decide the lifetime of playback,
routes and other business work. They can reuse an existing service and bus
connection when constructing the Python backend. Closing that SDK backend
releases only the service name it acquired itself.

The backend owns accepted actions through completion. After a presentation
closes, state publication still reaches its other sessions. Clients report
their pending operations as disconnected when their session ends. A new
session obtains a fresh snapshot, and application commands resume through
explicit caller requests.

The provider limits an application to 64 presentation sessions and each
session to 64 pending requests. Limit failures preserve the previous state.

Python backends can supply `on_lifecycle(backend)`. The callback runs after a
session opens, closes, changes activity or loses its bus owner, and after an
accepted request enters or leaves the backend. `session_count`,
`active_session_count` and `pending_count` describe those leases and operations.
`pending_count` includes work accepted by a presentation that has since closed.
An application may exit when it has zero sessions, zero pending requests and
zero business work. Explicit stop commands remain application decisions.

## Python backend

Initialize a GLib D-Bus main loop before creating the backend. An action handler
receives its parameters and an `Invocation`. It calls `complete(result, state)`
or `fail(code, message)`. Completion can be submitted from a worker thread.
The SDK serializes completion and state publication on the GLib thread.
Direct `Backend.publish(state)` calls run on that thread.

The counter reference backend opens in the background and serves both
presentations from one state owner. Its delayed action demonstrates a pending
request while the D-Bus loop remains responsive. [Reference backend](examples/counter-service.py)

Run these commands as the normal Sailfish session user in separate terminals.

```sh
python3 /usr/share/sailplay-sdk/examples/counter-service.py
python3 /usr/share/sailplay-sdk/examples/python-client.py --presentation car
python3 /usr/share/sailplay-sdk/examples/python-client.py --presentation phone
```

The example activation files are installed in the examples directory. For an
application integration, add the SDK metadata to that app's desktop declaration
and expose the backend under its existing Sailjail-granted service identity.
`ExecDBus` starts its background entry point. The reference service and desktop
declarations show the relevant fields. [Service declaration](examples/org.example.SailplayCounter.service)
[Desktop declaration](examples/sailplay-sdk-counter.desktop)

## Python client

Set `PYTHONPATH=/opt/sailplay` when importing the RPM's Python helper from another
application. A client activates the declared service if it has no owner,
negotiates capabilities, opens its session and subscribes to state updates.

```python
from dbus.mainloop.glib import DBusGMainLoop
from gi.repository import GLib
from sailplay_sdk.client import SessionClient

DBusGMainLoop(set_as_default=True)
client = SessionClient("org.example.SailplayCounter", presentation="car",
                       capabilities=("state", "actions"),
                       on_state=lambda revision, state: print(revision, state))
try:
    client.open()
    GLib.MainLoop().run()
finally:
    client.close()
```

Wait for `on_ready(True)` before invoking an action. `invoke` returns a local
request ID that is also supplied to `on_request`. The complete command-line
example includes completion and error handling. [Python client](examples/python-client.py)

## Qt5 and QML

Include the SDK in the application's qmake project.

```qmake
include(/usr/share/sailplay-sdk/qt/sailplay-sdk.pri)
```

`SailplaySession` exposes asynchronous `open`, `invoke`, `setActive` and `close`
methods. Its properties include readiness, application identity, capabilities,
revision and state. `requestFinished` and `errorOccurred` carry completion and
failure information. The example builds a console client from the same source.
[Qt client](examples/qt-client.cpp)

Applications using QML register the class before loading their component.

```cpp
qmlRegisterType<SailplaySession>("Sailplay.SDK", 1, 0, "SailplaySession");
```

```qml
import QtQml 2.0
import Sailplay.SDK 1.0

SailplaySession {
    onReadyChanged: if (ready) invoke("increment", {amount: 1}, revision)
    Component.onCompleted: open("org.example.SailplayCounter")
}
```

## Qt state and session providers

`SailplayProvider` exports App1 and caller-owned Session1 leases on an existing
application connection. Start the object before acquiring the activatable
application name, so a cold-start client can discover the SDK path immediately.

```cpp
#include "sailplayprovider.h"

auto bus = QDBusConnection::sessionBus();
SailplayProvider provider(bus, "example-media", {{"playing", false}}, {"media"});
if (!provider.start() || !bus.registerService("org.example.Media")) return 1;
provider.publish({{"playing", true}});
```

The provider embeds the canonical XML for introspection and argument checks.
`publish` validates typed state and returns whether publication succeeded.
Equal state retains its revision. `sessionCount`, `activeSessionCount` and
`sessionsChanged` support the application's exit policy. State and activity
signals are directed to their session owner. Caller loss releases its leases.
Media control uses MPRIS.

Register application actions with `setActionHandler` before starting the
provider. A handler receives a backend invocation token and typed parameters
on the provider's Qt thread. `Invoke` acknowledges acceptance before dispatch.
Call `complete(token, result)` or `fail(token, code, message)` when work ends.
`complete(token, result, state)` also checks the admitted revision before
publishing the replacement state. Exceptions from an action finish it with
`Failed`. Unsupported actions receive `NotSupported`.

`pendingCount` includes accepted work after its presentation closes.
`pendingChanged` supports the backend's exit policy. Each session admits 64
pending requests, and the Qt provider admits 4096 across live and closed
sessions. Publication and completion run on the provider's Qt thread.

Qt navigation providers initialize complete guidance with
`SailplayProvider::navigationGuidance()`, include it under `navigation`,
advertise the `navigation` capability and register `navigation.stop` before
`start`. Their caller-owned sessions export the canonical Navigation1 XML,
typed snapshots and directed guidance updates. The CMake provider retains
finite-distance validation when linked into an application using fast-math.

The SDK also provides a CMake `sailplay_sdk_provider` target. Its embedded XML
comes from `SAILPLAY_SDK_INTERFACES`, the repository interfaces directory or the
installed D-Bus interface directory. The native Mconnect integration supplies
the provider and XML through a guarded source overlay.
[Mconnect integration](integrations/mconnect/README.md)

## Navigation providers

`org.sailplay.Navigation1` is exported on each caller-owned navigation session.
`GetGuidance` returns the application revision and a native `a{sv}` guidance
model. `GuidanceChanged` delivers the same complete model to its session owner.
The regular Session1 snapshot includes that model under `navigation`, so both
existing language bindings share the same initial snapshot and reconnect flow.

Navigation1 requires the following fields and variant types.

| Field | D-Bus type | Meaning |
|---|---|---|
| `state` | `s` | `idle`, `active`, `unavailable`, `stopped` or `arrived` |
| `mode` | `s` | `driving`, `walking`, `cycling` or `transit` |
| `maneuver` | `s` | Provider-neutral maneuver name |
| `drivingSide` | `s` | `left` or `right` |
| `exitNumber` | `u` | Roundabout exit number, zero when unspecified |
| `nextDistanceMeters` | `d` | Finite, nonnegative distance to the maneuver in meters |
| `remainingDistanceMeters` | `d` | Finite, nonnegative remaining route distance in meters |
| `remainingSeconds` | `t` | Remaining route duration in seconds |
| `currentRoad` | `s` | Current road |
| `nextRoad` | `s` | Road after the maneuver |
| `destination` | `s` | Destination label |
| `updatedMs` | `t` | Actual guidance update time from `CLOCK_BOOTTIME`, in milliseconds |

Maneuvers are `unknown`, `continue`, `slight-left`, `slight-right`, `turn-left`,
`turn-right`, `sharp-left`, `sharp-right`, `uturn`, `roundabout-enter`,
`roundabout-exit`, `roundabout-continue`, `exit-left`, `exit-right` and `arrive`.
Each text field is bounded to 1024 Unicode characters. Inactive lifecycle states
clear previous road, distance and maneuver values.

Providers advertise `navigation` and implement the asynchronous
`navigation.stop` action. Other route-planning actions remain application-defined.
`NavigationBackend` validates publications and assigns explicit D-Bus variant
types. `guidance(...)` creates complete models with a suspend-aware timestamp.
Active guidance expires after ten seconds without a navigation update.
The car publisher's heartbeat independently expires after three seconds.

```python
from sailplay_sdk.guidance import guidance
from sailplay_sdk.navigation import NavigationBackend

def stop_navigation(parameters, invocation):
    stop_route_engine()
    backend.publish_guidance(guidance('stopped'))
    invocation.complete({'stopped': True})

backend = NavigationBackend('org.example.MyMap', 'my-map',
                            {'navigation.stop': stop_navigation})
backend.publish_guidance(guidance('active', maneuver='turn-right',
    nextDistanceMeters=200, remainingDistanceMeters=12000,
    remainingSeconds=900, currentRoad='Current road', nextRoad='Next road'))
```

`NavigationClient` reuses SessionClient and exposes validated `guidance` plus
an `on_navigation(revision, guidance)` callback. Qt clients can read the same
model from `SailplaySession.state["navigation"]`. Generated Navigation1 proxies
also accompany the Qt source SDK.

## Discovery and the car navigation template

The application declares its existing backend service and SDK capabilities in
its installed desktop file.

```ini
[Desktop Entry]
Type=Application
Name=My map
Exec=/usr/bin/my-map
ExecDBus=/usr/bin/my-map --background
X-Sailplay-ApiVersion=1
X-Sailplay-Service=org.example.MyMap
X-Sailplay-ObjectPath=/org/sailplay/v1/App
X-Sailplay-Capabilities=navigation;
X-Sailplay-Presentation=template
```

Python `read_declaration` and `discover` helpers, and Qt
`SailplayApplication::fromDesktopFile`, read these declarations. The car app list
accepts supported navigation templates. A tile or dock activation opens the
backend and its car session through D-Bus. Selecting the app for the dashboard
opens the compact guidance card. The expanded card offers an explicit stop
control. Backend identity must match the desktop-file basename.

Sailplay keeps the car session when the template is hidden and calls
`SetActive(false)`. Projection teardown releases its D-Bus connection and session.
The application decides whether its route continues. The same backend can serve
a separate phone presentation while the car template remains open.

For the existing CarPlay instrument sender, Sailplay publishes a private,
atomic SDK guidance snapshot from the car UI. The root-side reader validates
the publisher's executable, projection environment, PID, start time, boot ID,
ownership and freshness before using it. Revision and duration values retain
their full uint64 range across that local JSON envelope. Organic Maps v1 files
remain available through the legacy adapter. Multiple valid providers produce
an ambiguous state and clear instrument guidance. Instrument output currently
consumes driving guidance.

The fake navigation backend provides a simulator with start, stop and delayed
actions. Its route keeps updating while either SDK view closes. Run it and the
command client on a development bus.

```sh
python3 sdk/examples/navigation-service.py
python3 sdk/examples/python-client.py --service org.example.SailplayNavigation --action navigation.start
python3 sdk/examples/python-client.py --service org.example.SailplayNavigation --action navigation.stop
```

The example desktop and activation files ship under the examples directory.
An application's packaging installs its own declarations into the system
desktop and session-bus service directories. A second provider can use the same
contract under another existing application identity. The example backend
accepts `--service` and `--application-id` for that integration check.

Navigation1 and its template remain an experimental SDK extension. Native
Mconnect uses the media session provider for its window/core separation.
Organic Maps retains one framework, route, location source and writable state,
while its phone window can be released and rebuilt. Its car presentation uses
the navigation template. Dedicated map canvas rendering, Sailjail renderer
permissions and Content1 templates remain subsequent stages.
[Organic Maps integration](https://github.com/0312birdzhang/harbour-sailplay/tree/master/sdk/integrations/organicmaps)

## Validation

`tests/test_sdk_unittest.py` checks the XML signatures, ownership, snapshots,
request IDs, revision conflicts and resource limits. With Linux D-Bus and GLib
bindings available, it also runs the reference backend and Python clients on a
private bus, checks live introspection against the XML, activates a background
service, and exercises backend replacement with a new instance and revision sequence.

`tests/test_navigation_sdk_unittest.py` covers the fixed guidance model, desktop
declarations, legacy maneuver conversions, Unicode and uint64 snapshots, and
publisher identity and expiry. Its private-bus scenario also exercises the
reference backend's main entry point and graceful signal exit.

`tests/navigation_sdk_host_probe.pro` builds a Qt probe using the production
navigation host and SDK bindings. It checks phone closure, hidden car sessions,
explicit stop, Unicode state and private snapshot cleanup on Sailfish.

`tests/sdk_provider_test.pro` checks the Qt provider, caller-owned state and
properties, directed signals, resource limits and owner loss. Its production
music host checks hidden activity, player replacement and backend replacement.
The Mconnect integration adds native window and work lifetime regression suites
and repeated release/reload of the installed Silica QML tree. Installed and
physical phone/car verification are recorded separately in `todo.md`.

`tests/sdk_navigation_provider_test.pro` checks native Navigation1 signatures,
typed guidance, caller ownership, asynchronous completion, revision conflicts,
pending limits and accepted work after view closure or caller loss.
`tests/map_backend_probe.pro` checks viewport ownership, repeated QML release,
native driving and walking maneuver values, units and Unicode bounds.

`tests/map_backend_lifecycle_probe.cpp` builds through the existing test-only
map CMake hook. It uses the production Sailfish bridge, full phone QML and an
isolated copy of an installed offline map. It verifies window Close handling,
repeated renderer destruction/recreation, route progress and recording
statistics with the phone closed, saved recordings and explicit stop.
