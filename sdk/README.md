# Sailplay application SDK v1

The first SDK stage provides application and presentation-session contracts,
Python provider/client helpers, and a Qt5 client that can be registered in QML.
Applications expose the interfaces on their own session-bus service identity.

## Installed files

| Path | Contents |
|---|---|
| `/opt/sailplay/sailplay_sdk` | Python helpers and canonical XML |
| `/usr/share/dbus-1/interfaces/org.sailplay.App1.xml` | Application contract |
| `/usr/share/dbus-1/interfaces/org.sailplay.Session1.xml` | Presentation-session contract |
| `/usr/share/sailplay-sdk/qt` | Qt source and qmake include |
| `/usr/share/sailplay-sdk/examples` | Python/Qt clients, reference backend and activation metadata |

The RPM installs these files together with Sailplay. A Python wheel built from
this repository also includes `sailplay_sdk` and its XML. Wheel builds use a
current pip and Setuptools 77 or later on the build host.

## Wire contract

The default application path is `/org/sailplay/v1/App`. An application may
declare another versioned path in its desktop metadata. Interface versions
remain explicit in their names.

`org.sailplay.App1` exposes read-only `ApiVersion`, `ApplicationId`, `InstanceId`
and `Capabilities` properties. `OpenSession(presentation, requiredCapabilities)`
returns a caller-owned session object. Presentations are `phone` and `car`.
Required capabilities are matched against the application's advertised list.
The base capabilities are `state` and `actions`.

`org.sailplay.Session1` provides the following operations.

| Member | Behavior |
|---|---|
| `GetSnapshot` | Return the current `uint64` revision and `a{sv}` state |
| `SetActive` | Update whether the presentation is active |
| `Invoke` | Accept a request ID, action, `a{sv}` parameters and expected revision |
| `Close` | Release this presentation session |
| `StateChanged` | Deliver a complete replacement snapshot and its revision |
| `RequestFinished` | Deliver request ID, revision, result and error fields |

State and parameters use native D-Bus variants. Applications define the keys,
value types and action semantics within their advertised capabilities. String
keys are nonempty. Qt proxies are generated by qmake from the canonical XML.
The Python helpers read the same XML for method and signal signatures.
The Python provider checks each incoming SDK method's wire signature.

Request IDs start at one and increase within a session. Reusing an accepted ID raises
`org.sailplay.Error1.DuplicateRequest` before executing work. The method reply
acknowledges acceptance. Completion arrives asynchronously through
`RequestFinished`, including for an action that completes immediately.

Expected revision zero permits an unconditional operation. A nonzero revision
is checked before dispatch and before committing a replacement state supplied
to `Invocation.complete`. A stale admission fails the method. A conflict during
completion finishes the request with `org.sailplay.Error1.StaleRevision`.
Revisions increase when state changes.

The provider has a fresh `InstanceId` for every backend instance. Clients clear
their cached state when the service owner changes and obtain a new snapshot
after reconnecting. Clients subscribe before requesting the first snapshot and
keep the highest revision received within that instance.

## Session ownership and lifecycle

Each presentation belongs to the unique D-Bus name that opened it. Other
callers receive `org.sailplay.Error1.NotOwner` when accessing that session.
State and request-completion signals are addressed to the owning caller.
The provider releases sessions when their caller disconnects from the bus.

Closing a view should call `Close`. `SetActive(false)` keeps the session while
its presentation is hidden. Applications decide the lifetime of playback,
routes and other business work. They can reuse an existing service and bus
connection when constructing the Python backend. Closing that SDK backend
releases only the service name it acquired itself.

The backend owns accepted actions through completion. After a presentation
closes, state publication still reaches its other sessions. Clients report
their pending operations as disconnected when their session ends. A new
session obtains a fresh snapshot, and application commands resume through
explicit caller requests.

The provider limits an application to 64 presentation sessions and each
session to 64 pending requests. Limit failures preserve the previous state.

## Python backend

Initialize a GLib D-Bus main loop before creating the backend. An action handler
receives its parameters and an `Invocation`. It calls `complete(result, state)`
or `fail(code, message)`. Completion can be submitted from a worker thread.
The SDK serializes completion and state publication on the GLib thread.
Direct `Backend.publish(state)` calls run on that thread.

The counter reference backend opens in the background and serves both
presentations from one state owner. Its delayed action demonstrates a pending
request while the D-Bus loop remains responsive. [Reference backend](examples/counter-service.py)

Run these commands as the normal Sailfish session user in separate terminals.

```sh
python3 /usr/share/sailplay-sdk/examples/counter-service.py
python3 /usr/share/sailplay-sdk/examples/python-client.py --presentation car
python3 /usr/share/sailplay-sdk/examples/python-client.py --presentation phone
```

The example activation files are installed in the examples directory. For an
application integration, add the SDK metadata to that app's desktop declaration
and expose the backend under its existing Sailjail-granted service identity.
`ExecDBus` starts its background entry point. The reference service and desktop
declarations show the relevant fields. [Service declaration](examples/org.example.SailplayCounter.service)
[Desktop declaration](examples/sailplay-sdk-counter.desktop)

## Python client

Set `PYTHONPATH=/opt/sailplay` when importing the RPM's Python helper from another
application. A client activates the declared service if it has no owner,
negotiates capabilities, opens its session and subscribes to state updates.

```python
from dbus.mainloop.glib import DBusGMainLoop
from gi.repository import GLib
from sailplay_sdk.client import SessionClient

DBusGMainLoop(set_as_default=True)
client = SessionClient("org.example.SailplayCounter", presentation="car",
                       capabilities=("state", "actions"),
                       on_state=lambda revision, state: print(revision, state))
try:
    client.open()
    GLib.MainLoop().run()
finally:
    client.close()
```

Wait for `on_ready(True)` before invoking an action. `invoke` returns a local
request ID that is also supplied to `on_request`. The complete command-line
example includes completion and error handling. [Python client](examples/python-client.py)

## Qt5 and QML

Include the SDK in the application's qmake project.

```qmake
include(/usr/share/sailplay-sdk/qt/sailplay-sdk.pri)
```

`SailplaySession` exposes asynchronous `open`, `invoke`, `setActive` and `close`
methods. Its properties include readiness, application identity, capabilities,
revision and state. `requestFinished` and `errorOccurred` carry completion and
failure information. The example builds a console client from the same source.
[Qt client](examples/qt-client.cpp)

Applications using QML register the class before loading their component.

```cpp
qmlRegisterType<SailplaySession>("Sailplay.SDK", 1, 0, "SailplaySession");
```

```qml
import QtQml 2.0
import Sailplay.SDK 1.0

SailplaySession {
    onReadyChanged: if (ready) invoke("increment", {amount: 1}, revision)
    Component.onCompleted: open("org.example.SailplayCounter")
}
```

## Validation

`tests/test_sdk_unittest.py` checks the XML signatures, ownership, snapshots,
request IDs, revision conflicts and resource limits. With Linux D-Bus and GLib
bindings available, it also runs the reference backend and Python clients on a
private bus, checks live introspection against the XML, activates a background
service, and exercises backend replacement with a new instance and revision sequence.

Application adoption, Mconnect view lifetime and the sandboxed car renderer
remain integration milestones for the broader SDK proposal.
